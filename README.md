# ПроСобеседование

Telegram-бот с выбором роли и уровня, адаптивным текстовым и голосовым
интервью и персональным отчётом. Реализация по Техническому заданию
версии 2.0 от 11 октября 2026 года.

**Статус: Часть 5/5 — функциональный MVP завершён** (задачи ТЗ T02–T20,
T22–T24 реализованы; T01/T21–T23 частично — всё, что требует внешних
доступов, живых провайдеров, рецензента и фактического развёртывания,
перечислено в разделе «Условия запуска»). План разбиения —
[PROJECT_PLAN.md](PROJECT_PLAN.md); чеклисты соответствия — в `planning/`;
воспроизводимая проверка пакета — `verification/verify_spec.py`.

## Архитектура (кратко, §2.1 ТЗ)

Модульный монолит на Python: один репозиторий и один контейнерный образ,
два процесса — **API** (FastAPI: webhook + health) и **worker** (aiogram:
команды, AI-задания, исходящие сообщения). Между процессами — PostgreSQL
(транзакции, дедупликация, надёжные очереди `SELECT FOR UPDATE SKIP LOCKED`
+ lease). LLM/STT/TTS — через адаптеры провайдеров; без заполненного
`provider-profile.json` AI-вызовы блокируются.

## Структура репозитория (§3.10)

```
app/
  api/          # API-процесс: webhook, health, единый ErrorResponse
  telegram/     # внешний адаптер: разбор и классификация Update
  domain/       # правила: ошибки (§3.2), нормализация ответов (§3.3)
  services/     # оркестрация: UI-токены (22 символа, §3.1)
  providers/    # LLM/STT/TTS адаптеры (части 3–4)
  storage/      # PostgreSQL: пул, миграции, inbox-репозиторий
  workers/      # worker-процесс (обработчики — часть 2)
contracts/      # нормативные контракты 2.0: модели, семантическая
                # валидация, методы, state-machine, схемы, примеры
migrations/     # SQL-миграции (14 таблиц, §2.3)
config/         # settings.json, questions.json (36 записей), products.json,
                # provider-profile.example.json, .env.example
prompts/        # turn-system.txt, report-system.txt, user-envelope.txt (2.0)
scripts/        # генерация примеров/схем, webhook, backup/restore, smoke,
                # check_signals, load_test, манифест версий
deploy/         # init-db-roles.sql (роли app/migrator/backup)
diagrams/       # компоненты, потоки данных, сущности (SVG)
verification/   # verify_spec.py + spec-check.json (проверка пакета §5.1)
tests/          # unit + integration (требуется PostgreSQL); references/ —
                # 18 эталонов AT04/AT10
planning/       # чеклисты частей 1–5, WBS/оценки, матрица соответствия,
                # протоколы передачи, развёртывания и нагрузки
```

## Что сделано в части 5 (жизненный цикл, контроль, выпуск)

- **T18 — отмена/истечение/удаление** (`app/services/lifecycle.py`):
  истечение неактивных сессий (24 ч) с освобождением резерва и отменой
  jobs/outbox; удаление контента отменённых/истёкших (24 ч) и завершённых
  (30 дней) с сохранением минимальной терминальной записи sessions и
  обнулением current_turn_id; /report после очистки не восстанавливает
  содержание; черновики STT ≤1 ч; обнуление payload очередей ≤24 ч и
  дедлайн незавершённых; метаданные очередей 7 дней (unknown-затраты
  удерживаются до сверки, предел 90 дней); события/журнал затрат 90 дней;
  tombstones 7 дней; физическое /delete-удаление с медиа и tombstone
  (только внутренний UUID); повторное применение удалений по tombstones
  после restore ДО приёма трафика; сверка восстановленного inbox;
  поздние AI-результаты и старые кнопки не восстанавливают данные.
- **T19 — метрики и сигналы** (`app/services/metrics.py`, `monitoring.py`):
  учёт всех попыток API (исходы success/429/5xx/400/401-403/unknown/
  invalid_json по операциям assess/report/stt/tts), повторы, fallback/
  degraded, стоимость в микродолларах, report-delivery, STT-действия,
  задержки этапов p50/p95, обработка inbox и lease-expiry — без
  содержимого ответов; снимок очередей из БД раз в минуту (лог `metrics`);
  шесть сигналов оператору (oldest AI job >60 с; degraded >10% из 20;
  heartbeat worker >60 с; ошибка backup; 401/403 AI; остаток бюджета
  <20%) — ERROR-лог `operator_signal`, канал уведомлений задаётся перед
  запуском; одноразовая проверка `scripts/check_signals.py`; heartbeat —
  файл в RUN_DIR (схема БД остаётся 14 таблиц).
- **T20 — приёмочные сценарии** (`tests/integration/test_acceptance.py`):
  AT05 (10 дублей update + два конкурентных ответа), AT06 (старые кнопки,
  поздний AI после отмены/истечения/удаления), AT07 (краш до/после commit,
  неизвестный sendMessage, порядок отчёта), AT08 (429/5xx/невалидный JSON:
  ≤2 вызова, нет зависших lease, резерв), AT15 (credit: одна сессия,
  атомарность, освобождение при отказе, unknown-расход). Устранён дефект:
  «Завершить» из awaiting_answer помечает текущий вопрос пропущенным —
  report-задание больше не падает на неотвеченном turn.
- **T21 — эталоны AT04/AT10**: 18 наборов (3 роли × 2 уровня × 3 качества)
  в `tests/references/reference_sets.json` — ответы, ожидаемые рубрики,
  допустимые переходы, недопустимые выдуманные утверждения; автоматическая
  проверка переходов по правилам §3.3, 18 сквозных прогонов с отчётом
  (цитаты проверяемы, действия 1–3, degraded=0) и отклонение выдуманных
  цитат валидатором. Шаг сложности основного технического ответа
  применяется и в ветке уточнения (§3.3), уточнение использует сложность
  родителя. Предметная проверка рецензентом — условие запуска.
- **T22 — нагрузка**: jobs-worker обрабатывает задания конкурентно
  (in-flight = 5+2+2), семафоры ограничивают параллельность провайдеров;
  `scripts/load_test.py` — протокол 20 сессий с p95 шести этапов по меткам
  БД (локальный прогон: все p95 в целях §1.3, 20/20 completed);
  `planning/load-test-protocol.md` — шаблон протокола на staging.
- **T23 — развёртывание**: `scripts/set_webhook.py` (секрет +
  allowed_updates), `scripts/backup.sh` (pg_dump ролью backup, AES-256,
  скользящие 7 дней, статус для сигнала), `scripts/restore.sh` (трафик

  make_version_manifest.py` → `planning/version-manifest.json`;
  `deploy/init-db-roles.sql` (app/migrator/backup); compose: общий том
  RUN_DIR (heartbeat), ротация логов ~14 дней; `planning/
  deploy-checklist.md` — стартовая последовательность §3.10 и журнал RPO/RTO.
- **T24 — передача**: `planning/handoff-protocol.md` (повестка 45 мин,
  четыре сложные ситуации, шаблон фиксации), `planning/access-register.csv`

  `estimates.json` (90+18 ч, критический путь 58 ч, коммерция 30+6),
  `planning/checklist-matrix.csv` (69 детализаций требований),
  `verification/verify_spec.py` → `spec-check.json` (10 проверок
  согласованности пакета, шаг CI), `diagrams/*.svg`.

## Что сделано в части 4 (голос и отчёт)

- **T15 — приём аудио и ограничения**: скачивание voice через `getFile`
  с жёстким пределом 10 MiB (поток обрезается — отказ, не частичный файл);
  отказ по метаданным до скачивания; проверка OGG/Opus и фактической
  длительности ≤120 с изолированным декодером (`media_probe`: отдельный
  процесс, RLIMIT_AS 256 MiB, RLIMIT_CPU/wall 10 с, без shell); каталог
  0700, файлы 0600, случайные 32-символьные имена; суммарный предел
  256 MiB и число файлов на сервер — при заполнении новый голосовой вход
  отклоняется (`MEDIA_STORAGE_FULL`) без принятия ответа; удаление в
  `finally`, sweep каждые 5 минут, startup cleanup, максимум 1 час.
- **T16 — STT и подтверждение расшифровки**: transcribe-задание (≤2 STT-вызова
  на операцию, ≤3 запуска на вопрос); черновик `draft_transcript` с
  `transcript_version` (подтверждение защищено от старой записи); исправление
  текста (1–4000) и перезапись без расхода turn; пустая/>4000 расшифровка не
  засчитывается; сбой STT → возврат к ожиданию ответа (текст всегда доступен);
  голос во время расшифровки — BUSY.
- **T17 — TTS и возврат к тексту**: озвучивается только текст вопроса ≤700
  (без ответа пользователя), reply на доставленный текстовый вопрос,
  необязательная строка outbox; сбой озвучивания не блокирует интервью;
  ≤2 TTS-вызова на операцию, бюджет как у LLM; результат удаляется после доставки.
- **T13/T14 — отчёт и доставка**: снимок фактических вопросов/ответов/оценок
  (без Telegram ID); GenerateReportInput → FeedbackReport 2.0 (summary,
  strengths, gaps, 1–3 конкретных действия, next_steps); семантическая
  валидация цитат (буквально из ответов, NFC); ≤2 вызова на отчёт; при
  переполнении токенов или невалидном выводе — детерминированный запасной
  отчёт, помеченный degraded (без фиктивных цитат); ≤12000 символов, 1–4
  части ≤3500 (цитаты не рвутся); сохранение до отправки одной транзакцией;
  последовательная доставка, `delivery_started_at` до первой попытки, после —
  отмена возвращает BUSY; все части → completed + резерв → consumed;
  терминальный сбой доставки → failed с освобождением резерва; повторный
  `/report` без нового LLM-вызова; оценка полезности и «Новая тренировка».

## Что сделано в части 3 (AI-ядро интервью)

- **T11 — AI-адаптер и валидация контрактов**: `HttpLlmClient`
  (OpenAI-совместимый endpoint, aiogram-независимый, опциональный api_base
  для локального Bot API/LLM-сервера); классификация исходов по §3.2
  (429 retry_after / 5xx и сеть — повтор / 400 — фатально / 401·403 —
  сигнал оператору); не более 2 вызовов провайдера на операцию (учёт через
  `ai_calls UNIQUE(job_id, attempt)` — предел держится и между перезапусками
  задания); таймаут вызова 20 с, общий дедлайн оценки 110 с; температура 0.2;
  строгий разбор одного JSON-объекта + структурная (TurnAssessment 2.0) и
  семантическая валидация (цитаты буквально из ответа, пары
  correctness/evidence, turn_id).
- **Бюджет и стоимость (§1.3, §3.10)**: транзакционный резерв стоимости до
  вызова; успех заменяет резерв фактом; известный отказ освобождает;
  неизвестный результат → `unknown_usd` до сверки; токен-бюджет сессии
  100000/22000 с неприкосновенным резервом отчёта 24000/7000 →
  BUDGET_EXCEEDED: «Подготовим разбор уже полученных ответов»; суточный
  лимит блокирует дорогие вызовы, сохраняя права пользователя; очередь AI
  ≤60 с, затем запасной сценарий; семафор 5 параллельных LLM-вызовов.
- **T12 — Адаптация и запасные переходы**: jobs-worker (SKIP LOCKED + lease
  120 с + heartbeat 20 с, expected_version — поздний результат устаревшей
  версии отбрасывается); фиксированное серверное правило действия
  (уточнение ≤1 на вопрос и ≤2 на сессию; «не знаю»/relevance=0 → дальше);
  шаг сложности ±1 с границами intern 1–2 / junior 1–3 (HR и уточнения
  сложность не меняют); вопрос модели принимается только валидным
  (длина ≤700, без управляющих символов, тематическая проверка по лексике
  рубрики каталога), иначе вопрос каталога; requested_action=finish —
  оценка применяется, новая тема не создаётся; запасные сценарии
  AI_UNAVAILABLE/AI_INVALID_OUTPUT: «Интервью продолжается с ограниченной
  оценкой», следующий вопрос из каталога, оценка NULL; обновление статуса
  «Обработка занимает больше времени» один раз после 15 с ожидания (§3.7);
  полный план из 6 вопросов → reporting + report-задание (исполнение —
  часть 4).
- История оценок передаётся модели в пределах 12000 токенов с сокращением
  по старым объяснениям, текущий ответ не сокращается (§3.3).

## Что сделано в части 2 (worker-процесс)

- **T06 (worker)** — inbox-обработчик: транзакционная обработка с ≤5
  повторами, фаза 1 вне транзакции (быстрый ack callback, групповое
  уведомление), откат частичных эффектов при доменной ошибке и уведомление
  в новой транзакции, восстановление просроченных lease.
- **T10** — outbox-sender: aiogram-адаптер Bot API с классификацией исходов
  (429 retry_after / 403 чат недоступен / 400 ошибка реализации / сеть —
  повтор), ≤10 повторов в 24 ч с backoff, порядок question_text/report_part
  («следующий обязательный текст не отправляется, пока предыдущий не
  подтверждён»), 1 отправка/с на чат и ≤20/с глобально, повторная проверка
  признака удаления и отменённой сессии перед отправкой, confirmation-хуки:
  message_id вопроса сохраняется, сессия delivering_question →
  awaiting_answer; терминальный отказ доставки → failed + освобождение
  резерва (§2.4).
- **T07** — вход и выбор: /start, уведомление об AI-обработке и сроках
  хранения, кнопка согласия (версия документа 2.0 + дата), отказ оставляет
  /help; выбор роли → уровня → формата отдельными сообщениями с inline-
  кнопками и «Назад»; сводка параметров; одноразовые ui_tokens (30 мин /
  5 мин / 24 ч), привязка к владельцу и разрешённому значению; устаревшая
  кнопка → актуальный экран; кампания-код только из allowlist.
- **T08** — старт сессии: транзакция users → sessions → credits с резервом
  trial-попытки (порядок trial → grant → payment), лимиты (3 старта/24 ч —
  отменённые и неудачные учитываются; 10 команд/мин → RATE_LIMITED с
  retry_after), фиксация версий каталога/промпта/профиля, первый вопрос из
  каталога (ForceReply) + отдельное сообщение управления «Пропустить /
  Завершить / Отменить» [S1], событие start.
- **T09 (транзакционная половина)** — приём текстового ответа: проверка
  reply на подтверждённый message_id текущего вопроса (и его известные
  копии), нормализация и границы 1–4000, атомарно: ответ + версия сессии +
  уникальное assess-задание + подтверждение «Ответ принят. Готовлю
  следующий вопрос.»; двойной ответ → BUSY без нового задания и без
  перезаписи; события answer_accepted/first_answer.
- Управление сессией: пропуск (запись без оценки, переход к следующей
  основной теме; все пропущены → cancelled + «Попытка сохранена»),
  «Завершить» (во время оценки → requested_action=finish; без ответов →
  NO_ANSWERS + освобождение резерва; с ответами → reporting +
  report-задание), «Отменить» с отдельным подтверждением (→ cancelled +
  освобождение резерва), /status, /report (пустые состояния и повторная
  доставка сохранённого отчёта без нового LLM), /balance, /delete с
  подтверждением (deletion_requested_at, отмена сессии и очередей, блокировка
  новых действий; физическое удаление — часть 5).
- Голосовые сообщения: в text-формате отклоняются с предложением текста;
  в voice-формате до подключения STT (часть 4) разрешён текстовый ответ —
  выдаётся честная подсказка (§3.5).

AI-задания (assess/report) создаются и ожидают обработчики частей 3–4:
принятые ответы не теряются, состояние сессии видно в /status.

  36 основных записей (2 HR + 4 технических на сценарий) с рубриками,

  проверка рецензентом до публичного выпуска.

  с `manifest.json` (16 валидных/невалидных примеров), `contracts/schemas/`
  (35 JSON Schema, производные от моделей), `methods.json`,
  `state-machine.json`.
- **T06 (API)** — `POST /telegram/webhook/{route_token}`: секрет
  (403), route_token (404), только JSON (415), ≤1 MiB (413), неверная

  вызова AI, PostgreSQL недоступен — 503; `GET /health/live`,
  `GET /health/ready` без раскрытия секретов и адреса БД.
- Startup-валидация конфигурации (§3.6): инварианты лимитов, токенов,
  таймаутов/SLO, каталога, секретов; незаполненный provider-profile
  блокирует AI, но не webhook.
- Основы домена: единый `ErrorResponse` и реестр кодов §3.2; нормализация
  и граничные длины ответа (NFC, LF, управляющие символы, 0/1/4000/4001
  кодовых точек, без молчаливого обрезания); UI-токены 16 байт → 22 символа;
  механизм выборки inbox (SKIP LOCKED + lease + ≤5 повторов).

## Локальный запуск

Требования: Python 3.11+, PostgreSQL 15+, (для контейнеров) Docker.

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt

cp config/.env.example .env   # заполните BOT_TOKEN, WEBHOOK_SECRET,
                              # WEBHOOK_ROUTE_TOKEN, DATABASE_URL

# миграции (ролью миграций; в dev допустима роль приложения)
python -m app.storage.migrate

# API-процесс
python -m app.api.main        # http://127.0.0.1:8080/health/live
```

Docker Compose (db + api; worker — профиль `workers`, миграции — `migrate`):

```bash
docker compose run --rm migrate
docker compose up -d db api
```

TLS терминирует внешний reverse proxy: webhook публикуется только по HTTPS
с установленным `setWebhook(secret_token=WEBHOOK_SECRET,
allowed_updates=["message","callback_query"])` (§3.1, §3.10).

## Тесты

```bash
export TEST_DATABASE_URL=postgresql://app:...@127.0.0.1:5432/prosob_test
pytest -q          # 574 теста: unit + integration против реальных PostgreSQL и Bot API/LLM/STT/TTS-стабов

```

Интеграционные тесты сбрасывают схему БД с именем, содержащим `test`;
при недоступной БД они пропускаются (unit-часть работает без БД).

## Безопасность и данные (§3.9)

- Секреты только в окружении (`config/.env.example` перечисляет имена);
  в репозиторий не включаются.
- В логах: request_id, код ошибки, вид задания, время — без содержимого
  ответов, расшифровок и AI-payload.
- `/health/ready` и ошибки не раскрывают ключи и адрес БД.
- `provider-profile.json` (рабочая копия) в `.gitignore`.

## Порядок чтения пакета (§5.1) и самопроверка

1. `PROJECT_PLAN.md` — разбиение на части и состав задач ТЗ.
2. `README.md` (этот файл) — архитектура, структура, запуск, тесты.
3. `planning/handoff-protocol.md` — повестка передачи и четыре сложные
   ситуации; `planning/access-register.csv` — проверки доступов.
4. `planning/wbs.csv` + `estimates.json` — план и часы;
   `planning/checklist-matrix.csv` — соответствие требованиям.
5. `contracts/` — нормативные модели, схемы, примеры (manifest),
   state-machine; `config/` и `prompts/` — правила версии 2.0.
6. `planning/part1..5-checklist.md` — требование → реализация → проверка.
7. `planning/deploy-checklist.md` и `load-test-protocol.md` — запуск и
   нагрузочная приёмка; `diagrams/*.svg` — компоненты, потоки, сущности.

Воспроизводимая проверка согласованности пакета (без БД и сети):

```bash
python verification/verify_spec.py        # обновляет verification/spec-check.json
python verification/verify_spec.py --check  # только проверка (используется CI)
```

Проверка подтверждает согласованность спецификации, а не предметную точность
вопросов, реальную задержку провайдеров или работающий бот (для этого
T21–T23 и сценарии AT01–AT17).
