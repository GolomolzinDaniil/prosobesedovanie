# План реализации «ПроСобеседование» по ТЗ версии 2.0

Полный объём ТЗ: 90 часов разработки (T01–T24) + 18 часов резерва (R01–R03).
Проект разделён на 5 условных частей примерно по 18 часов. Каждая часть
заканчивается рабочим, тестируемым состоянием репозитория.

## Часть 1/5 — Фундамент (✅ выполнена, ≈18 ч)

Задачи ТЗ: **T02, T03, T04, T05, T06 (API-часть)**.

| Результат | Задача ТЗ | Где |
|---|---|---|
| Структура репозитория по §3.10, контейнеры, CI | T02 | `Dockerfile`, `docker-compose.yml`, `.github/workflows/ci.yml` |
| Модель данных: 14 таблиц, ограничения, индексы, миграции | T03 | `migrations/0001_initial.sql`, `app/storage/` |
| Каталог: 6 сценариев роль × уровень, 36 основных записей с рубриками, запасными вопросами и советами | T04 | `config/questions.json` |
| Промпты версии 2.0 + нормативные контракты и примеры | T05 | `prompts/`, `contracts/` |
| Webhook: секрет, лимиты 1 MiB/JSON, inbox с дедупликацией по update_id, HTTP 200/400/403/413/415/503 | T06 | `app/api/`, `app/telegram/`, `app/storage/inbox_repo.py` |
| Health-эндпоинты live/ready без раскрытия секретов | §3.1 | `app/api/routes/health.py` |
| Конфигурация settings/products/provider-profile/.env.example + startup-валидация по §3.6 | §3.6 | `config/`, `app/config.py` |
| Механизм выборки заданий SELECT FOR UPDATE SKIP LOCKED + lease | §2.1 | `app/storage/inbox_repo.py`, `tests/integration/test_inbox_claim.py` |
| Нормализация и граничные длины ответа (0/1/4000/4001), кодовые точки Unicode | §3.3 | `app/domain/answers.py` |
| Ошибки: единый ErrorResponse, реестр кодов §3.2 | §3.2 | `app/domain/errors.py` |
| UI-токены: 16 байт base64url без padding = 22 символа | §3.1 | `app/services/ui_tokens.py` |

Критерий готовности части: миграции применяются к чистому PostgreSQL;
`docker compose up` поднимает API; webhook корректно сохраняет обновления
в inbox с дедупликацией и всеми кодами ответов; startup-валидация ловит
несогласованные конфигурации; unit- и integration-тесты проходят; примеры
контрактов (валидные и невалидные) проверяются по manifest.json.

## Часть 2/5 — Worker и начало диалога (✅ выполнена, ≈18 ч)

Задачи ТЗ: T06 (worker-часть), T07, T08, T10.

- Inbox-worker: транзакционный обработчик с ≤5 повторами, дедупликация эффектов.
- Outbox-sender: 1 msg/s на чат, ≤20/s суммарно, 429 retry_after, ≤10 повторов/24 ч.
- Вход: /start, согласие (версия+дата), выбор роли/уровня/формата через ui_tokens, сводка.
- Старт сессии: транзакция users → sessions → credits, резерв trial-попытки, первый вопрос из каталога.

## Часть 3/5 — Ядро интервью (✅ выполнена, ≈18 ч)

Задачи ТЗ: T09 (reply/owner/version-проверки), T11, T12, начало T21.

- Приём текстового ответа: reply на подтверждённый message_id, владелец, версия, BUSY/STALE_ACTION.
- AI-адаптер LLM: бюджет, ≤2 вызова на операцию, таймауты 20/35 с, валидация TurnAssessment.
- Адаптация: правило уточнений (≤1 на вопрос, ≤2 на сессию), шаги сложности, отбраковка вопросов модели, запасные переходы (AI_UNAVAILABLE → вопрос из каталога).

## Часть 4/5 — Голос и отчёт (✅ выполнена, ≈18 ч)

Задачи ТЗ: T13, T14, T15, T16, T17.

- Приём voice: getFile, предел 10 MiB, OGG/Opus, длительность ≤120 с, изолированный декодер, cleanup/sweep.
- STT: задание, черновик, transcript_version, подтверждение/исправление/перезапись (≤3 запуска на вопрос).
- TTS: озвучка вопроса после текста, сбой не блокирует интервью.
- Отчёт: GenerateReportInput, FeedbackReport 2.0, семантическая валидация цитат, детерминированный запасной отчёт (degraded), разбиение на 1–4 части по 3500, доставка, consumed-credit, /report без нового LLM.
- Delivery_started_at до первой попытки; отмена после — BUSY «отчёт уже отправляется» (§2.4).

Итог: 422 теста, ruff clean; детали — `planning/part4-checklist.md`.

## Часть 5/5 — Жизненный цикл, контроль, выпуск (✅ выполнена, ≈18 ч)

Задачи ТЗ: T18, T19, T20, T22, T23, T24 (+ механика T21).

- Отмена/истечение/удаление: lifecycle-sweeps (expiry 24 ч, контент 24 ч/30 дней, payload 24 ч, метаданные 7 дней, события/затраты 90 дней), tombstones, повторное применение после restore, поздние AI-результаты не восстанавливают данные.
- Метрики всех попыток API и задержек этапов (без контента), шесть сигналов оператору, heartbeat worker, статус backup, check_signals.py.
- Приёмочные сценарии AT05–AT08, AT15; 18 эталонов AT04/AT10 (наборы + автоматическая проверка переходов и отчётов; рецензент — условие запуска); нагрузка AT14 (конкурентный jobs-worker 5/2/2, load_test.py — протокол 20 сессий, p95 в целях §1.3).
- Развёртывание: set_webhook/backup/restore/smoke/version-manifest, роли БД, ротация логов, deploy-checklist; передача: handoff-protocol, access-register, wbs/estimates, checklist-matrix (69 строк), verify_spec.py (10 проверок, CI), диаграммы.

Итог: 574 теста, ruff clean, verify_spec 10/10; детали — `planning/part5-checklist.md`.

Коммерческий контур (P01–P06, Telegram Stars) — после функционального MVP,
в отдельной итерации; в части 1 схема `payments` создаётся пустой для FK `credits`.

## Принятые решения и допущения части 1

1. Архив спецификаций (contracts/, diagrams/, planning/) к ТЗ не передан —
   нормативные контракты восстановлены по тексту ТЗ версии 2.0 в `contracts/`
   и используются как единственный источник форматов.
2. Неверный `route_token` webhook возвращает 404 (не раскрывает существование
   точки); неверный секрет — 403 согласно §3.1.
3. Обновления неподдерживаемых видов сохраняются в inbox со статусом `skipped`
   (признаны обработанными без вызова AI, §3.1) — для дедупликации и аудита.
4. `pre_checkout_query` при `billing_enabled=false` считается неподдерживаемым
   видом (коммерческий этап отдельный).
5. Незаполненный `provider-profile.json` (null-значения) не блокирует webhook
   и health, но блокирует AI-вызовы (§1.4: «запуск блокируется» относится
   к AI-интеграциям; готовность сервиса по §3.10 зависит от БД и конфигурации).
6. Роли БД: приложение и миграции разделены на уровне документации/compose;
   в dev допускается одна роль.
